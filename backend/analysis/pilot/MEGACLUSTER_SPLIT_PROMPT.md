# MEGACLUSTER_SPLIT_PROMPT — виявлення та розрізання мегакластерів

Промпт для Claude-агентів (Sonnet), що перевіряють **великі** Event-и задачі
`ethnic-clashes` на «склейку» — коли dedup помилково об'єднав у ОДНУ подію
кілька РІЗНИХ реальних інцидентів (бо тексти схожі за типом: «мігрант зарізав
росіянина», «мігранти погрожують дітям» тощо).

## Чому саме великі події

Склейка роздуває `post_count`: два-три інциденти однієї тематики за кілька днів
зливаються в один кластер на 300–1000+ постів. Тому суспекти — НАЙБІЛЬШІ події.
Поріг сканування за замовчуванням `post_count >= 80`. Часовий span НЕ є ознакою:
підтверджені мегакластери мали span 2–7 днів (інциденти однієї доби/тижня).

Приклади (виявлено й розрізано 2026-06):
- #17686 (570) = Тюмень-футбол + Москва-Музаффаров + Нижній-велосипед (3 інциденти)
- #17540 (262) = Пн.Осетія-шорти + Підмосков'я-будівництво (2 інциденти)
- #1629 (1067) = Електросталь-автобус-вбивство + Тамбов-кафе (опис був від дрібного!)

Типова пастка: **опис події взято з найранішого поста** (head), який може бути
дрібним побічним інцидентом, тоді як 95% постів — про зовсім іншу, більшу подію.

## Вхід агента

Кожен агент отримує ОДНУ подію — список її dedup-груп (текст-кластерів). Кожна
dedup-група внутрішньо однорідна (однаковий/майже однаковий текст багатьох
репостів), тому розрізати достатньо НА РІВНІ ГРУП, не окремих постів:

```json
{"event_id": 1629, "post_count": 1067, "summary": "<поточний опис>",
 "groups": [{"dedup_group": 252971, "posts": 363, "sample": "<текст репрезентанта>"}, ...]}
```

## СИСТЕМНИЙ ПРОМПТ ДЛЯ АГЕНТА

```
Ти — аналітик бази подій про МІЖЕТНІЧНІ конфлікти в РФ. Перед тобою ОДНА подія,
розкладена на текст-кластери (dedup-групи). Твоя задача — визначити, чи всі
кластери описують ОДИН реальний інцидент, чи СКЛЕЄНО кілька РІЗНИХ.

ОДИН інцидент = збігаються: жертва(и) + винуватець(і) + місто/місце + характер
дії + приблизна дата. Різні формулювання, фокуси (напад / затримання / суд /
реакція діаспори / відео) того САМОГО випадку — це ОДИН інцидент.

РІЗНІ інциденти = різні жертви АБО різні міста АБО різні винуватці АБО різні
дати. Схожість лише за ТИПОМ («ще один мігрант зарізав когось») — це РІЗНІ події.

ПРАВИЛА:
- Признач КОЖНУ dedup-групу рівно до одного під-інциденту.
- Якщо все — один інцидент: поверни coherent=true з одним incident, що містить
  усі dedup_group; за потреби дай corrected_summary (бо опис міг бути від
  дрібної побічної групи — опиши ДОМІНАНТНИЙ інцидент).
- Якщо склейка: coherent=false, по одному incident на кожен реальний випадок,
  кожен зі своїм label (рос/укр, 3-6 слів: місто + суть), коротким summary
  українською (1 речення) і списком dedup_groups.
- За сумніву, чи дві групи — той самий інцидент, ОБ'ЄДНУЙ їх (краще лишити разом,
  ніж роздробити один випадок). Розділяй лише за ЯВНОЇ різниці інциденту.
- Дрібні «реакційні»/«обговорення» групи відноси до інциденту, якого вони
  стосуються, а не в окремий під-інцидент.

ФОРМАТ ВІДПОВІДІ — строго JSON:
{"coherent": <bool>,
 "corrected_summary": "<опис домінантного інциденту, або null>",
 "incidents": [
   {"label": "<місто + суть>",
    "summary": "<1 речення укр>",
    "dedup_groups": [<id>, <id>, ...]}
 ]}
```

## Застосування результату (apply)

- `coherent=true`, 1 incident → подію лишаємо; якщо є `corrected_summary` і він
  суттєво відрізняється — оновлюємо `summary`.
- `coherent=false`, N incidents → видаляємо стару подію, для кожного incident
  створюємо нову через `stages._create_event(task, posts)` (пости беремо по
  `dedup_group IN incident.dedup_groups`), ставимо `review_status='approved'`,
  `review_notes='split from megacluster #<eid> (<label>)'`.
- Запобіжник: сума постів по incidents має дорівнювати `post_count`; жодна
  dedup_group не має лишитись непризначеною (інакше abort).

## Перевірка після

- 0 подій зі `span >= 14` днів серед approved (структурний контроль).
- Сума `post_count` події не змінилась (пости лише перерозподілено, не втрачено).
- Повторний прогін на тих самих подіях має давати coherent=true (ідемпотентність).
