# Простий інтерфейс (`/app/`) — дизайн, етап 1

> Окремий шар для користувача з навичками нижче середнього: читає результати,
> сам запускає збори, налаштування міняє через асистента, збої не розгрібає.
> Django-адмінка лишається «експертним режимом» і не переробляється.
> Стан на 2026-09-21, гілка `feature/simple-ui`. Код: `backend/simpleui/`.

## 1. Принципи

- **Секція = задача моніторингу** (`AnalysisTask`), названа людською мовою.
  Ніяких `task 13 pipeline infospace`.
- **Спочатку результат, потім механіка.** Верх екрана — світлофор і цифри,
  далі графіки, далі стрічка. Механіка (джерела, розклад) — на окремій сторінці.
- **≤ 7 понять на екрані:** стан, період, подія, регіон, тема, джерело, збір.
- **Не показуємо взагалі:** review_status/аудит, стадії постів, prescreen,
  чанки, воркери, «Чекає агента», pipeline, slug, id задачі, промпти, моделі
  LLM, TeleZip-синтаксис, пости-джерела у стрічці, reach.
- **Той самий логін і та сама видимість**, що в адмінці: `LOGIN_URL` веде на
  форму адмінки; суперюзер бачить усі задачі, інші — лише `task.owner == user`
  (той самий критерій, що в `EventAdmin.get_queryset` і
  `mcp_api.common.scope_tasks`).
- **Ті самі цифри, що в адмінці:** агрегації тільки через
  `analysis/services/metrics.py` (`EventSource`), лише `review_status=approved`
  (дефолт адмінки), гео — `region_subject`.
- **Той самий Chart.js** (`analysis/vendor/chart.umd.min.js`), що в
  `_charts_body.html`; тема — спокійна, великий шрифт, 3 кольори стану + 1 акцент.
- **Мобільна ширина** — одна колонка від 360px, великі кнопки-цілі.

## 2. Карта екранів

```
/app/                         Список секцій (стартова)
  └─ /app/<task_id>/           Секція: світлофор → графіки → стрічка
       ├─ ?period=week|month|quarter|custom&from=&to=   (єдиний контрол)
       ├─ /app/<task_id>/settings/           Налаштування (окрема сторінка, лише читання)
       ├─ /app/<task_id>/event/<event_id>/   Картка події
       └─ /app/<task_id>/collect/            Майстер «Зібрати за період» (заглушка)
```

### 2.1 Список секцій `/app/`
Картка на кожну видиму задачу: людська назва, підзаголовок (опис, 1 рядок),
світлофор, «сьогодні / за тиждень», «оновлено N хв тому». Спочатку живі,
далі зупинені (сірі). Клік по картці → секція.

### 2.2 Секція `/app/<id>/`
1. **Світлофор стану** (`simpleui/services/status.py`, §4).
2. **Період** — 3 кнопки-пресети + «свій» (два поля дат). Один контрол на всі
   графіки й стрічку.
3. **Графіки** (4, готові дефолти, жодних налаштувань):
   - «Скільки подій» — динаміка (стовпчики; день для тижня/місяця, тиждень для
     кварталу) — `EventSource.timeseries()`;
   - «Де відбувалося» — топ-10 регіонів (горизонтальні стовпчики) —
     `EventSource.by_region()`;
   - «Про що» — топ-10 тегів головної категорії задачі —
     `EventSource.by_tag(category)` (§3.3);
   - «Хто пише найбільше» — топ-10 джерел (Source / канал) — прямий COUNT по
     `Post` подій зрізу (це не аналітична метрика, а довідка про джерела).
3а. **Фільтри** (`simpleui/services/filters.py`) — ті самі, що в адмінці подій, з
   тими самими іменами параметрів URL (`region_id`, `tag_<cat>`, `tag_<cat>_excl`,
   `channel_id`/`source_id`, `channel_count__gte`, `q`), тож посилання
   взаємозамінні. Фасетні лічильники — на зрізі з усіма іншими фільтрами, як в
   адмінці. Впливають на графіки і стрічку разом. Активні фільтри — чіпами над
   стрічкою. Не переносимо: статус аудиту й задача (зафіксовані), охоплення,
   спецфільтри задачі етносутичок.
4. **Стрічка подій** — останні 30 за період: заголовок (перше речення опису),
   дата, регіон, джерело. Без постів і статусів. Клік → картка.
5. **Кнопки:** «Налаштування» (окрема сторінка), «Зібрати за період» (майстер).

### 2.3 Картка події `/app/<id>/event/<eid>/`
Дата, регіон + населений пункт, повний опис, теми (теги людськими назвами
категорій із `TagCategory.label`, без `importance`), «Де про це писали» —
посилання на оригінали (назва джерела/каналу + дата). Без аудиту, без reach.

### 2.4 Сторінка «Налаштування» `/app/<id>/settings/` (лише читання)
- Одне речення людською мовою: «Стежимо за N джерелами у M регіонах,
  оновлюємо кожні ~X хв, публікуємо в …» (§4.3 — за конвеєром).
- Список джерел, згрупований по регіонах (назва, тип: Telegram/RSS/сайт).
- «Як працює збір» — УСІ налаштування задачі, згруповані по етапах конвеєра
  так само, як у формі адмінки (`AnalysisTaskAdmin._FS_*` — одне джерело
  правди для групування). Значення перекладені: так/ні, назви категорій,
  порожній промпт = «стандартне (з коду)», довгі тексти згорнуті. help_text
  і технічні описи етапів не показуємо.
- Блок «Змінити через асистента»: 3–5 готових фраз із кнопкою «Скопіювати».
  Полів для редагування НЕМАЄ. Фрази підставляють назву секції й приклад
  регіону з її джерел, напр.:
  «Додай канал @… у моніторинг „{назва}“ для {регіон}»,
  «Прибери джерело „…“ з „{назва}“»,
  «Покажи, які джерела „{назва}“ мовчать понад добу»,
  «Збери „{назва}“ за минулий тиждень»,
  «Перейменуй секцію „{назва}“ на „…“».

### 2.5 Майстер «Зібрати за період» (заглушка, етап 1)
Кроки на одній сторінці: період (пресети «минулий тиждень / минулий місяць /
свій»), оцінка (запитів TeleZip ≈ днів ÷ `collect_chunk_days` × джерел-за-
каналом; ціна ≈ запитів × $0.10; час ≈ запитів × ~20 с), кнопка «Запустити»
показує «Запуск зʼявиться на етапі 2». Реального `ResearchRun` не створює.
Для infospace-задач (безперервний полінг) сторінка пояснює, що збір іде сам,
а перезбір за період — етап 2.

## 3. Словник людських назв

### 3.1 Назва секції — звідки
**Рішення: нове поле `AnalysisTask.display_name`** (CharField 120, blank,
`db_default=""`, міграція `0081`). Порожньо → показуємо `name`. Правиться в
адмінці (розділ «Загальне» форми задачі) або асистентом (`task_update`).
Альтернатива через `Setting simple_ui_names_json` відкинута: назва — атрибут
задачі, а не глобальний конфіг; поле видно поруч із задачею і в MCP.

Заповнено в dev: 13 → «Інформпростір регіонів», 3 → «Критика влади в
республіках», 19 → «Критика федеральної влади: Сибір і Далекий Схід»,
1 → «Міжетнічні сутички», 24/25 → «Вибори-2026: канали / чати».

### 3.2 Стани (світлофор)

| Показуємо | Колір | Коли |
|---|---|---|
| **Працює** | зелений | задача активна, свіжі дані, немає збоїв |
| **Є проблема** | жовтогарячий | активна, але: джерела мовчать / збої / збір упав / черга стоїть |
| **Зупинено** | сірий | `is_active=False` |

Підпис під станом — одна фраза: «оновлено 12 хв тому», «джерела мовчать
19 год», «останній збір упав», «5 джерел не відповідають». Далі «Сьогодні: N ·
За тиждень: M» (події за `event_date`, approved).

### 3.3 Переклад внутрішніх понять

| Внутрішнє | Людською | Де |
|---|---|---|
| `AnalysisTask` | секція | всюди |
| `pipeline=infospace` | «оновлюється сам, кожні ~X хв» | шухляда |
| `pipeline=monitor/events/research` | «збір за період на запит» | шухляда, майстер |
| `pipeline=tgsearch` | «стежимо за чатами в Telegram» | шухляда |
| `ResearchRun.status=collecting` | «Збираємо зараз» | світлофор |
| `awaiting_agent`, пости на стадіях | «Обробляємо зібране» | світлофор |
| `failed` (run/chunk/source ≥3) | «Є проблема» | світлофор |
| `Source.kind` telegram/rss/web | Telegram / стрічка сайту / сайт | шухляда |
| `MonitorChat` | чат у Telegram | шухляда |
| `Event.summary` | опис; перше речення = заголовок | стрічка, картка |
| `Tag.category` → `TagCategory.label` | «Тема», «Виборча кампанія»… | картка, графік |
| `importance` | не показуємо | — |
| `review_status` | не показуємо (беремо лише approved) | — |
| `PublishConfig` активний | «публікуємо в „назва профілю“» | шухляда |

Головна категорія тегів для графіка «Про що»: перша з `task.tag_categories`
(за `TagCategory.order`), крім `importance`; якщо порожньо — категорія з
найбільшою кількістю подій у зрізі.

## 4. Що переюзаємо

| Потреба | Існуюче |
|---|---|
| видимість | критерій `owner`/суперюзер (`EventAdmin.get_queryset`, `mcp_api.common.scope_tasks`) |
| логін | `LOGIN_URL=/admin/login/`, `@login_required` |
| агрегації | `analysis.services.metrics.EventSource` (`timeseries`, `by_region`, `by_tag`) |
| графіки | `analysis/vendor/chart.umd.min.js`; палітра/патерни з `_charts_body.html` |
| стан infospace | `Source.last_ok_at / consecutive_failures / quality_ok / is_active`, `Post.created_at` |
| стан збору | `ResearchRun.status/finished_at`, `CollectChunk.status/next_retry_at`, `Post.stage` (`mcp_api.service.NON_TERMINAL`) |
| джерела | `SourceSubscription` (infospace), `MonitorChat` (monitor/tgsearch/research), `telezip_query` (events — не показуємо текст, лише «пошук по Telegram») |
| публікація | `PublishConfig(task=, is_active=True)` |
| людські назви категорій | `TagCategory.label` |
| фрази для асистента | інструменти MCP `source_update`, `chat_update`, `run_create`, `task_update` — фрази сформульовані так, щоб асистент зміг їх виконати наявними інструментами |

Нові ендпоінти: лише HTML-вʼюхи `backend/simpleui/views.py` (`/app/…`), без
нового API. Дані графіків вбудовані в сторінку JSON-блоком, як у адмінці.

## 5. Що свідомо НЕ робимо на етапі 1

- жодного запису в БД із `/app/` (усе GET, майстер — макет);
- жодних змін конвеєрів і моделей, крім `display_name`;
- жодного виклику Telegram/TeleZip;
- без пошуку/фільтрів по стрічці, без експорту — етап 2 після відгуку.

## 6. Етап 2 (орієнтовно)
Реальний запуск збору з майстра (`run_create` через той самий код, що MCP),
всі секції (не лише прототип), сповіщення «є проблема» у Telegram, картка
регіону, пошук у стрічці.
