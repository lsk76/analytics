# Конвеєр `tgsearch` — пошук у чатах через Telegram

> **Статус:** дизайн, 31.08.2026. Народився із задачі «прикордонні чати»: треба
> знайти, де саме люди говорять про перетин кордону, і зробити з цих розмов події.

## 1. Ідея за один абзац

П'ятий конвеєр поруч із `events`, `monitor`, `research`, `infospace`. Відрізняється
від усіх наявних одним: **збір іде серверним пошуком самого Telegram**, а не
суцільним потоком. Ми не вичитуємо чат цілком — питаємо в Telegram «покажи в цьому
чаті повідомлення зі словом X за тиждень» і працюємо лише з влученнями.

```
канали/чати  ->  пошук у Telegram (балансування по акаунтах)
             ->  фільтр релевантності (ШІ API)
             ->  тегування (ШІ API)
             ->  Event (1 повідомлення = 1 подія, текст коментаря видно в адмінці)
```

## 2. Чому не підійшов жоден наявний

| конвеєр | чому не годиться |
|---|---|
| `monitor` | збирає **суцільний потік** коментарів через TeleZip і тегує **агентами Claude**. Нам не треба весь потік — треба влучення за словами; і тегувати треба API, а не хвилями агентів |
| `events` | дедупить N постів у 1 подію; тут навпаки — кожне повідомлення це окрема репліка людини |
| `research` | працює періодами по каналах через TeleZip, без пошуку в межах чату |
| `infospace` | безперервний полінг джерел; пошуку за словами немає |

Головний технічний аргумент: **TeleZip не гарантує покриття дрібних груп** і має
внутрішній ліміт 2 хв на запит (широкий запит він ріже). Telegram-пошук читає
першоджерело і відповідає точно по кожному чату.

## 3. Що реюзаємо, що нове

| крок | рішення | донор |
|---|---|---|
| скелет воркера, claim-черга по `Post.stage` | реюз | усі конвеєри |
| моделі `Post`, `Event`, `Channel`, `Tag` | реюз | усі |
| **список чатів** = `MonitorChat` (task ↔ channel + `tg_account`) | реюз **як є** | `monitor` |
| **пошук у чаті через Telethon** | **новий** | — |
| **балансування по акаунтах** | реюз принципу | `border_resolve.py`, `monitor_sample_collect` |
| фільтр релевантності через ШІ API | реюз | `monitor` (`mon_prescreen`) |
| тегування через ШІ API | **новий** (у monitor це агенти) | частково `services/tags.py` |
| матеріалізація події 1:1 | реюз | `monitor_stages.sync_comment_event` |

`MonitorChat` підходить без змін: у ньому вже є і задача, і канал, і `tg_account` —
саме те, що потрібно для балансування. Заводити окрему таблицю підписок немає сенсу.

## 4. Стадії

Префікс `tgs_` (роутинг воркера — по префіксу стадії, як у решти).

### `tgs_search` — збір
Для кожного `MonitorChat` задачі: серверний пошук Telegram по кожному слову зі
списку задачі, вікно `search_days`, стеля `search_limit_per_term` на слово.

- **балансування:** чат читає той акаунт, що записаний у `MonitorChat.tg_account`;
  якщо порожній — призначається round-robin і **зберігається**. Це не оптимізація:
  резолв юзернейма кешується в сесії того акаунта, що резолвив, тож читати чат
  іншим акаунтом означає платити резолв удруге;
- **пауза** між запитами в межах акаунта, `FloodWait` зупиняє лише свій акаунт;
- на виході `Post` зі `stage=tgs_collected`, `content_hash` для дедупу повторів
  між прогонами (те саме повідомлення знайдеться і завтра).

Стадія працює **по задачах**, не по джерелах — тобто звичайний `_tasks()`-цикл.

### `tgs_screen` — фільтр релевантності (ШІ API)
Батч повідомлень → `prescreen_model` з `prescreen_prompt` задачі → так/ні.
Нерелевантні йдуть у `done` з `is_relevant=False` (не видаляємо: знаменник
«скільки переглянули» потрібен для частки).

Навіщо взагалі фільтр, якщо пошук уже за словами: слово «граница» так само стоїть
у новинному репості й у переносному сенсі, а назви переходів — у фрахтових
оголошеннях. На розвідці по Кулунді 1826 постів зі словом у тексті дали майже
самі вантажні біржі.

### `tgs_tag` — тегування (ШІ API)
Батч релевантних → `tagger_prompt` задачі → теги за категоріями з
`task.tag_categories`. **Нова категорія тегів вимагає рядка `TagCategory`** —
інакше фасет-фільтр адмінки падає на `?e=1` (граблі з AI-GUIDE §1.6).

### `tgs_event` — подія
1 повідомлення → 1 `Event`, без дедупу (як у `monitor`: репліка людини — окрема
одиниця, злиття вбило б лічильник «скільки людей»). Механіка — та сама
`sync_comment_event`: `Post` лишається джерелом події, тож **текст коментаря
видно в картці події в адмінці**.

## 5. Нові поля `AnalysisTask`

| поле | тип | навіщо |
|---|---|---|
| `search_terms` | `TextField` | слова пошуку, по одному в рядок. Telegram **не вміє OR** — кожне слово це окремий запит, тож сміттєві слова сюди класти дорого |
| `search_days` | `int`, дефолт 7 | глибина вікна |
| `search_limit_per_term` | `int`, дефолт 100 | стеля влучень на слово в одному чаті |

Промпти й моделі беруться з наявних полів (`prescreen_model`, `prescreen_prompt`,
`tagger_prompt`) — окремих заводити не треба.

## 6. Що ще треба зробити

1. `PIPELINE_TGSEARCH = "tgsearch"` у `AnalysisTask.PIPELINE_CHOICES`;
2. три стадії в `Post.STAGE_CHOICES` (`tgs_collected`, `tgs_screened`, `tgs_tagged`);
3. `services/tgsearch_stages.py` з чотирма ранерами + реєстрація в `ALL_RUNNERS`;
4. гілка `stage.startswith("tgs_")` у `run_worker._tasks`;
5. картка етапів конвеєра у формі задачі (`get_fieldsets` + `CARDS` у
   `analysistask/change_form.html`), інлайн чатів уже є;
6. чотири воркери в `docker-compose.yml`;
7. міграція (усі поля з дефолтами, тож швидка).

## 7. Межі, про які треба памʼятати

- **Telegram-пошук не вміє OR** — вартість лінійна від кількості слів. Сім слів на
  400 чатів це ~2800 запитів; на 28 акаунтах ≈ 100 на акаунт, у межах норми;
- **пошук бачить лише те, що індексує Telegram** — дуже старі або видалені
  повідомлення не знайдуться;
- **стеля на слово** означає, що в дуже жвавому чаті число влучень занижене;
  для нього це «≥ ліміту», а не точна кількість;
- **кількість влучень ≠ якість джерела.** Група обговорення новинного каналу може
  дати влучення самими репостами. Частка людських повідомлень (`human_msgs_per_day`
  у довіднику) лишається обовʼязковою для відбору.
