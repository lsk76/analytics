# План: агент-ранер (автозапуск Claude Code на етапах, де потрібні агенти)

**Дата:** 21 серпня 2026.
**Проблема одним реченням:** два етапи конвеєра — агентне тегування коментарів і
агент-аудит подій — досі запускаються вручну через людину, тому весь конвеєр
привʼязаний до чийогось ноутбука і зупиняється, коли цієї людини немає.

---

## 1. Куди саме вбудовується

Конвеєр уже автоматичний з обох боків від діри:

```
mon_collect → mon_filter → mon_prescreen
      ↓
mon-runs воркер: готує батчі у _dir/runs/run_<id>/  →  status = awaiting_agent
      ↓
      ⚠️ ДІРА: тут потрібна людина, яка скаже Claude Code «протегуй батчі запуску N»
      ↓
агенти пишуть batch_NNN_done.json
      ↓
mon-runs воркер: _try_ingest бачить *_done.json → інжест → Event 1:1 → status = done
```

Те саме для подій: `ev_runs_once` → `awaiting_agent` → агенти пишуть keep/reject →
`_ev_try_ingest` закриває запуск.

**Тобто дописати треба рівно одну ланку** — те, що перетворює `awaiting_agent` на
`*_done.json`. Усе до і після вже працює й не змінюється.

Файли-донори: `analysis/services/pipeline_runs.py` (статуси, `batch_dir`,
`_try_ingest`), команди `monitor_prepare_batches --require-prescreen`,
`monitor_ingest_tags`.

## 2. Компоненти

| компонент | що робить | де живе |
|---|---|---|
| **watcher** | бачить `ResearchRun.status == awaiting_agent`, бере оренду на запуск, кличе launcher | новий воркер `agent-runner` (за конвенцією `run_worker._tasks`) |
| **launcher** | запускає `claude -p` із фіксованим промптом, моделлю, лімітом бюджету й вузьким набором інструментів | `services/agent_runner.py` |
| **звірка повноти** | після кожної хвилі: у кожному `*_done.json` рівно стільки елементів, скільки у вхідному; неповні — видалити й перетегувати | `services/agent_runner.py`, обовʼязковий крок, не опційний |
| **звіт у БД** | прогрес і результат видно в адмінці на сторінці запуску | поля на `ResearchRun` |

**Оренда обовʼязкова.** Без неї два цикли watcher-а запустять один запуск двічі й
подвоять витрати. Патерн уже є в проєкті — `locked_at` на `Source` в infospace.

---

## 3. Інваріанти, які зашиваємо в КОД, а не в інструкцію

Усі чотири — з власного досвіду проєкту, кожен уже коштував грошей або якості.

**Виконавець — тільки Haiku-агенти, і він не змінюється між періодами.**
Gemini на каноні v4 ігнорує ворота й старшинство: 51% замість 41.7% і пласка
розкладка тегів. Модель має бути прибита в конфігу запуску, а не залежати від
дефолту сесії. Зміна виконавця між періодами ламає динаміку непомітно — цифри
лишаються правдоподібними, а порівнювати їх уже не можна.

**Рівно стільки елементів, скільки на вході.** Агент має схильність тихо
скорочувати пачку. Перевірка — арифметична, після кожної хвилі.

**Жодних вкладених агентів.** Інакше одна хвиля породжує лавину й бюджет
вибухає.

**Стеля витрат на кожен запуск.** `claude -p --max-budget-usd`. Без неї кнопка
«запустити тегування» — це дуже дорогий клік: повний потік це ~47 тис.
кандидатів на місяць ≈ 946 пачок ≈ 16 млн токенів, саме тому запуск #30 зупинили
на 131-й пачці. Ранер мусить триматися погодженої вибіркової сітки, а не гнати
все підряд.

---

## 4. Безпека headless-сесії

Сесія працює на проді, де sudo без пароля, база на 128 тис. подій і 28 Telegram-сесій.
Тому ранер запускає Claude **не** з повними правами:

- `--allowedTools` — лише читання й запис у теці конкретного запуску;
- ніякого Bash до бази й docker;
- `--permission-mode` без інтерактиву, але й без `bypassPermissions`;
- робоча тека — `_dir/runs/run_<id>/`, а не корінь проєкту.

Це той самий принцип, що й з MCP: агент отримує рівно те, що потрібно для
тегування пачки, і нічого більше.

---

## 5. Як перевіряємо, що ранер працює правильно

**У нас є готовий еталон.** Запуск #30 (лютий 2026, канон v4) має **131 пачку,
відтеговану вручну погодженим процесом**. Це регресійний набір:

1. ганяємо ранер по тих самих вхідних пачках у пісочниці;
2. порівнюємо частку релевантних (еталон дав 41.7% від кандидатів) і розкладку
   тегів (має домінувати `крит_рег_правит`);
3. розбіжність по частці більш ніж на 2-3 в.п. або пласка розкладка = ранер
   поводиться як gemini, а не як канон, і його не можна пускати в роботу.

Без цієї перевірки ранер можна запустити, але не можна довіряти його числам.

## 6. Етапи

| # | що робимо | оцінка |
|---|---|---|
| 0 | інфраструктура: Node LTS + Claude Code на сервері, `claude setup-token`, памʼять | 1 год |
| 1 | `services/agent_runner.py`: launcher + звірка повноти, запуск руками по одному запуску | 3-4 год |
| 2 | регресія на 131 пачці запуску #30, звірка з еталоном | 2 год |
| 3 | воркер `agent-runner` з орендою + поля прогресу на `ResearchRun` | 3 год |
| 4 | кнопка в адмінці на сторінці запуску + показ прогресу й витрат | 2 год |
| 5 | те саме для агент-аудиту подій (`ev_runs`) — та сама механіка, інший промпт | 2 год |

**Разом ~2 робочі дні.** Порядок важливий: етап 2 перед етапом 3. Спершу
переконуємось, що ранер відтворює канон, і лише потім даємо йому запускатися
самому.

## 7. Ризики

**Мовчазна деградація якості** — головний. Ранер працює, статуси зелені, а теги
поступово розʼїжджаються. Лікується етапом 2 і періодичною перезвіркою на
еталоні, а не довірою до зелених статусів.

**Витрати.** Стеля на запуск обовʼязкова, плюс звіт по витратах у адмінці, щоб
було видно, скільки коштував кожен запуск.

**Часткові хвилі.** Неповні `done`-файли не можна інжестити — вони дадуть
заниження, яке виглядатиме як реальне падіння критики. Звірка повноти + видалення
неповних файлів.

**Зависання сесії.** Сьогодні тричі ловили, як `docker compose exec` не
завершується після роботи скрипта, і як Telethon на мертвій проксі йде в
нескінченні ретраї. Ранер мусить мати таймаут на запуск і позначати запуск як
`failed` з причиною, а не висіти.

---

## 8. Що потрібно до старту

- памʼять на сервері (в роботі);
- Node LTS + Claude Code + `setup-token` на сервері;
- рішення по вибірковій сітці: ранер тегує все підряд чи тримається сітки
  «кожна 3-тя пачка + поріг прескріну ≥0.6» (§ переробка кампанії вирівнювання
  в `docs/AI-GUIDE.md`).
