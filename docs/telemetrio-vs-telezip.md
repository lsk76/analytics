# Telemetr.io Public API — клієнт, спроможності, план тесту проти TeleZip

**Статус на 2026-09-01: клієнт готовий, тести проведені частково.**
Пошук по повідомленнях **вимкнено на нашому ключі**, тому головне порівняння
(head-to-head пошуку) провести не вдалося. Виміряно все інше — див. §5.

- Docs / пісочниця: <https://api.tlmtr.io/rapidoc>
- OpenAPI: <https://api.tlmtr.io/api-docs/openapi.json> (3.1.0)
- База: `https://api.tlmtr.io`, авторизація — заголовок **`x-api-key`** (не Bearer)
- Код: [`backend/analysis/services/telemetrio.py`](../backend/analysis/services/telemetrio.py)

## 1. Що є в API

| Ендпоінт | Навіщо нам |
|---|---|
| `GET /v1/search/messages` | **головне** — пошук по всіх постах каналів. *Alpha preview, за замовчуванням ВИМКНЕНО* |
| `GET /v1/messages/channel` | стрічка одного каналу за вікно (курсорна пагінація) |
| `GET /v1/messages/group` | повідомлення групи/чату — найближче до наших коментарів |
| `GET /v1/channels/search` | пошук каналів за назвою/описом/лінком; фільтри country/language/category |
| `GET /v1/catalog/search` | каталог — дискавері нових каналів |
| `GET /v1/channel/info`, `/v1/channels/info-batch` | єдине місце, де є `telegram_id` і `link` (t.me) |
| `GET /v1/channel/stats`, `/v1/group/stats`, `/v1/charts/*` | ERR, охоплення, динаміка підписників |
| `GET /v1/channel/mentions` | згадки каналу |
| `GET /v1/utils/resolve_telegram_id` | tg numeric id → внутрішній `internal_id` |
| `GET /v1/usage/info` | квоти. **Безкоштовний, у квоту не рахується** |

## 2. Спроможності: TeleZip vs Telemetr.io

Це порівняння **не потребує ключа** — воно випливає зі схеми API, і саме воно,
а не цифри повноти, визначає, які конвеєри взагалі можуть переїхати.

| | TeleZip | Telemetr.io |
|---|---|---|
| Пошук по всьому індексу | `POST /Find` | `GET /v1/search/messages` (Alpha, вмикають вручну) |
| **Булева мова запиту** | `+` AND, `-` NOT, `"фраза"`, `"a b"~N`, `слово*`, словоформи | **лише `"фраза"` в лапках.** Ні AND, ні NOT, ні proximity, ні префікса |
| Обмежити пошук каналами | `channelIds[]` / `channelNames[]` — масив | `on_channel` — **рівно один** канал |
| Мовний фільтр повідомлень | `languages: ["ru"]` | немає; є лише `country`/`category` **каналу** |
| Дедуп репостів | `unique=true` | немає |
| Глибина історії | весь індекс | free-ключ: **7 днів** |
| `reply_to` / `top_message_id` | є | **немає** |
| Автор повідомлення | `FromUserId` + `FromUserName` | лише `from_peer` (id), імені немає |
| t.me-лінк на пост | `messageUrl` готовий | **немає в пошуку**; лише через `channel/info` (їсть квоту каналів) |
| Метрики поста | немає | `views`, `forwards`, `comments`, `reactions`, `is_ad` |
| Видалені пости | немає | `deleted_at` — видно, що пост зняли |
| Статистика каналу | бідна | ERR, reach, графіки підписників |
| Модель ліміту | запити, 2 одночасні (слоти в БД) | 2-вимірна: запити + **унікальні терміни/канали** |

### Три висновки, які випливають прямо звідси

1. **Monitor-конвеєр (критика) переїхати НЕ може.** Він тримається на
   `reply_to`/`top_message_id` (прив'язати коментар до поста) і на
   `FromUserId`/`FromUserName` (дедуп «один автор у багатьох чатах»,
   `Post.also_in_chats`, `author_tg_id`). У Telemetr.io цих полів немає в жодному
   ендпоінті — див. `docs/comments-analysis-pipeline.md`.
2. **Events-конвеєр втрачає AND/NOT.** Наша робоча форма запиту —
   `(тема) +(дія) -(шум)`; на пілоті task=1 саме AND зрізав 11 404 → 367
   кандидатів (~31×). Без нього Telemetr.io поверне сирий потік, і фільтрація
   переїде в наш LLM-скрін — тобто ×20–30 до вартості скріну на той самий вихід.
   Компенсація можлива структурними фільтрами (`country`, `category`,
   `on_channel`) і кількома окремими запитами, але **кожен окремий термін
   коштує квоту** (див. §3).
3. **`Post.url` з пошуку не збирається.** `Post` має `unique_together (task, url)`
   — url це не косметика, а ключ дедупу. Пошукова відповідь дає лише
   `internal_id` + `message_id`; t.me-лінк живе тільки в `channel/info`, який їсть
   квоту унікальних каналів. Тому `parse_message()` лишає `message_url` порожнім,
   якщо йому не передали мапу лінків — вигадувати permalink не можна.

## 3. Квоти: рахуються ЧОТИРИ речі окремо

Виміряно на нашому ключі 2026-09-01 через `/v1/usage/info` — **цифри не збіглися
з тими, що озвучили при видачі** (казали 1000 пошукових запитів і 5 термінів):

| Вісь | Ліміт (факт) | Що її їсть |
|---|---|---|
| `requests` | 1000 / міс | будь-який виклик |
| `search_terms` | **10** / міс | кожен **новий** рядок `term`. Незворотно |
| `search_messages_requests` | **100** / міс | кожна сторінка пошуку |
| `channels` | 5 / міс | кожен **новий** `internal_id`; повторне читання того самого каналу в межах періоду безкоштовне |

Плюс: **лише verified канали/чати** («by Telegram **or Telemetr.io**» — тобто
їхній власний, ширший білий список) і **лише останні 7 днів**.

Мораль: `/v1/usage/info` безкоштовний — читати його, а не вірити на слово.
Кожна наша команда друкує дельту квот «до/після», тож ціна ендпоінта
вимірюється, а не вгадується.

**Виміряна ціна операцій:**

| Операція | requests | channels | terms |
|---|---|---|---|
| `usage/info` | 0 | 0 | 0 |
| `channels/search` | 1 | **0** | 0 |
| `resolve_telegram_id` | 1 | **0** | 0 |
| `messages/channel`, 1 сторінка (~22 повідомлення) | 1 | 1 (лише за перший дотик) | 0 |
| будь-яка **відмова** (400 про доступ) | 0–1 | **0** | **0** |

Останній рядок важливий: помилки доступу нічого не коштують, тож промацувати
межі тарифу безпечно.

`search_terms` лишається найдефіцитнішим ресурсом. API повідомляє *скільки*
термінів витрачено, але **не каже, які саме**, тому клієнт веде локальний реєстр
`TermLedger` (`.telemetrio_terms.json`, у `.gitignore`), і команди відмовляються
палити нові терміни без явного дозволу.

## 4. Спосіб тестування

Порядок продиктований ціною: спершу все, що коштує 0 термінів.
Етапи 0–2 **виконані** (результати — §5); етап 3 заблокований вендором.

### Етап 0 — ключ і квоти (0 витрат) ✅

```bash
docker compose exec web python manage.py telemetrio_probe
```
Показує статус підписки, всі чотири лічильники, вікно білінгу і локальний реєстр
термінів. Кожна команда друкує ще й **дельту квот «до/після»** — так фактична
ціна кожного ендпоінта вимірюється, а не вгадується (документація вказує ціну
не для всіх).

### Етап 1 — чи є в Telemetr.io наш корпус (0 термінів, 0 квоти каналів) ✅

```bash
docker compose exec web python manage.py telemetrio_channels --coverage --per-type 40 --with-region --random
```
Бере по 40 наших каналів кожного `chat_type` і питає Telemetr.io про кожен через
`resolve_telegram_id`. Виводить знає / трекає в розрізі типів.

**`--random` обов'язковий.** Без нього вибірка йде по топу за підписниками і
завищує покриття чатів у 2–5 разів (§5.2) — великі канали індексують усі.

**Ворота:** частка `tracked` серед `chat`/`discussion`. Результат — 45% і 18%.

### Етап 2 — повнота стрічки каналу (0 термінів, 1 унікальний канал) ✅

```bash
docker compose exec web python manage.py telemetrio_channels \
    --messages --username rian_ru --days 7 --max-pages 45 --vs-telezip
```
Тягне стрічку за 7 днів (`/v1/messages/channel` для каналів, `/v1/messages/group`
для чатів — на групі перший поверне порожньо) і зіставляє **за нормалізованим
текстом** з двома джерелами: нашою `Post` і, за `--vs-telezip`, тим самим каналом
з TeleZip (`searchTerm="*"` + `channelNames`).

`--vs-telezip` — це і є чесне порівняння **повноти індексів**, яке не витрачає
пошукових термінів. Поки Alpha-пошук вимкнено, це єдиний доступний вимір якості.

Брати канал з **активного** моніторингу; на free-ключі це впирається в
verified-only (§5.4).

### Етап 3 — head-to-head пошук (тут і тільки тут палимо терміни) ⛔ ЗАБЛОКОВАНО

Не запускається: `/v1/search/messages` вимкнено на ключі (§5.1). Команда нижче
готова і перевірена — вона коректно розпізнає відмову й не палить термін;
запускати одразу після того, як @telemetrio_support увімкне доступ.

```bash
# спершу завжди dry-run: покаже ціну і що саме новe
docker compose exec web python manage.py telemetrio_vs_telezip --term "мобилизация" --dry-run

docker compose exec web python manage.py telemetrio_vs_telezip \
    --term "мобилизация" --days 7 --country russia \
    --out /app/backend/_dev/tm_vs_tz
```

Один **голий** термін (без `+`/`-`) йде в обидва API на однаковому вікні —
це єдина чесна одиниця порівняння, бо мови запитів у них різні. Зіставлення —
за `sha1` нормалізованого тексту. Звіт: скільки знайшов кожен, перетин,
**яку частку TeleZip-знахідок покрив Telemetr.io**, скільки каналів з кожного
боку, скільки з них verified, час, і — головне — **дамп ексклюзивних знахідок
кожної сторони** у JSON. Цифри повноти без цих текстів нічого не варті: треба
очима подивитись, ЩО саме пропустив кожен і чи це релевантне.

**Бюджет термінів (фактичний ліміт — 10/міс, витрачено 0):**

| # | Термін | Що з'ясовує |
|---|---|---|
| 1 | широкий, напр. `мобилизация` | базове порівняння + чи взагалі працює. Заодно: **чи є морфологія** — глянути у видачі, чи трапляються `мобилизации`/`мобилизацию`. TeleZip словоформи ловить; якщо Telemetr.io ні — це ще один множник до втрати повноти |
| 2 | тематичний із живої рубрики, напр. `мигранты` | повнота на реальній задачі |
| 3 | точна фраза в лапках, напр. `"специальная военная операция"` | чи фразовий пошук поводиться як обіцяно |
| 4+ | **не витрачати** | резерв: перепитати вже оплачені терміни безкоштовно скільки завгодно, тож спершу вичавити максимум із 1–3 |

Морфологію можна перевірити **без окремого терміна**: шукати `мигранты` і
порахувати у дампі тексти, де є `мигрантов`, але немає `мигранты` (одне не є
підрядком іншого). Якщо таких нуль — лематизації немає, і це ще один множник
до втрати повноти проти TeleZip.

Терміни 1–3 можна ганяти повторно з різними `--country`, `--days`, `--max-pages`
без жодних додаткових витрат по осі термінів — саме так і треба знімати решту
питань.

## 5. Що виміряно 2026-09-01

### 5.1. Пошук по повідомленнях — НЕДОСТУПНИЙ

```
GET /v1/search/messages → HTTP 400 {"message":"Messages search is disabled"}
```
Це Alpha preview, вимкнений за замовчуванням. Віддається як **400, а не 403**,
попри те що це питання доступу — клієнт розпізнає цей текст окремо і повертає
`TelemetrioAccessError`. Виклик не коштує ні запиту, ні терміна.
**Поки @telemetrio_support не увімкне — головне питання «чи краще він шукає»
лишається без відповіді.**

### 5.2. Покриття нашого корпусу — головна цифра

`resolve_telegram_id` по 40 каналів кожного типу, лише з `region_subject`,
**випадкова** вибірка (`--random`):

| chat_type | знає | ТРЕКАЄ |
|---|---|---|
| `channel` (мовлення) | 40/40 | **39/40 — 98%** |
| `chat` (чат/група) | 40/40 | **18/40 — 45%** |
| `discussion` (linked-обговорення) | 40/40 | **7/40 — 18%** |

Та сама вибірка, але **топ за підписниками**, дає 100% / 78% / 92% — тобто
вибірка «по великих» завищує покриття в 2–5 разів на чатах. Чесна цифра — перша
таблиця. `tracked=false` означає: канал відомий, але статистика по ньому не
збирається, отже його повідомлень у пошуку не буде — і це **не залежить від
тарифу**.

Читати так: **мовлення покрите повністю, обговорення — ні.** Наш корпус критики
живе саме в чатах і linked-обговореннях.

### 5.3. Повнота стрічки каналу — паритет із TeleZip

`@rian_ru`, 7 днів, той самий канал і вікно в обидва API
(TeleZip: `searchTerm="*"` + `channelNames`, тож терміни Telemetr.io не витрачались):

| | повідомлень | зіставних |
|---|---|---|
| Telemetr.io | 455 | 420 |
| TeleZip | 422 | 420 |

Перетин **411**; взаємне покриття **97.9%**; ексклюзивних по 9 з кожного боку.
Тобто на каналі, який Telemetr.io трекає, **індекси рівноцінні** — питання не в
якості індексу, а в тому, які канали в нього взагалі потрапляють (§5.2).

Бонусом Telemetr.io показав **3 видалені пости** (`deleted_at`) — сигнал, якого
в TeleZip немає взагалі.

### 5.4. Наш робочий корпус на free-ключі недоступний

Усі 4 активні чати border-конвеєра (`VerhniyLars`, `verkhniy_lars_dariali`,
`georgia_lars`, `appbugristoe1`) відмовили:

```
GET /v1/messages/group → HTTP 400
{"message":"For free you have access only for verified by Telegram or Telemetr.io chats"}
```
Отже перевірити повноту саме по нашому корпусу можна **лише на платному тарифі**.

### 5.5. `channels/search` шукає за НАЗВОЮ, а не за username

`@toporlive` і `https://t.me/toporlive` обидва впевнено віддають *інший* канал
(«Топор», 1439 підп.) замість нашого «Топор Live», хоча документація обіцяє
підтримку username і t.me-лінків. Username у відповіді немає взагалі, тож
перевірити збіг нічим. **Єдиний надійний спосіб зіставити наш канал з їхнім —
`resolve_telegram_id` за Telegram numeric id.** Обмеження verified-only на цей
ендпоінт не поширюється (у видачі є `verified=false`).

## 6. Критерії рішення

**Замінити TeleZip** можна, лише якщо виконано ВСЕ:
- покриття наших каналів ≥ 80% — **ПРОВАЛЕНО для чатів**: 45% (`chat`) і 18%
  (`discussion`) проти 98% для мовлення (§5.2). Для events-конвеєра (мовлення)
  ворота пройдені;
- Telemetr.io покриває ≥ 80% TeleZip-знахідок на однакових термінах — **не
  перевірено**, пошук вимкнено (§5.1). Непрямий сигнал добрий: на стрічці
  трекнутого каналу індекси збігаються на 97.9% (§5.3);
- на платному тарифі є глибина > 7 днів і достатньо термінів, щоб виразити наші
  рубрики окремими запитами;
- знайдено, чим замінити відсутній AND/NOT — і порахована вартість LLM-скріну
  сирого потоку.

**Monitor-конвеєр (критика) не переїжджає в жодному разі** — немає `reply_to`
і імені автора (§2.1).

**Проміжний вердикт: не заміна, а доповнення.** Виміряне цього не спростувало —
там, де Telemetr.io трекає канал, він рівний TeleZip (97.9%) і дає зверху те,
чого в TeleZip немає; там, де живе наш корпус критики (чати й обговорення), він
просто не збирає дані. Корисне:
- `views` / `forwards` / `reactions` / ERR — метрик, яких у TeleZip немає взагалі,
  а для «ваги» події вони прямо корисні;
- `deleted_at` — видалені пости як окремий сигнал;
- `channels/search` + `catalog/search` — дискавері каналів замість парсера tgstat
  (`tools/discovery/tgstat_parser/`); але як **резолвер** username вони не годяться
  (§5.5) — лише як пошук нових каналів за темою/назвою;
- другий незалежний індекс для перехресної перевірки повноти TeleZip.

## 7. Питання до вендора (@telemetrio_support / contact@telemetr.io)

0. **Увімкнути `/v1/search/messages`** — без цього головне питання не має
   відповіді. Зараз віддає 400 `Messages search is disabled`.
1. Чи можна підняти покриття `chat`/`discussion` (45% / 18%) — це наш корпус;
   чи є спосіб замовити трекання конкретного списку чатів?
2. Чи є на платних тарифах булеві оператори (AND/NOT/proximity) або хоча б
   кілька термінів в одному запиті?
3. Ліміти платних тарифів: глибина історії, унікальні терміни/канали, чи знімається
   verified-only.
4. Чи планується `reply_to`/`top_message_id` і `from_user_name` у `/v1/messages/group`?
5. Чи можна отримувати t.me-permalink прямо в пошуковій відповіді (без
   `channel/info`, який їсть квоту каналів)?
6. Ліміт одночасних запитів (не документований).
